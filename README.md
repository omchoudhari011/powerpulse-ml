# PowerPulse ML - Building Energy Demand Forecasting (model module only)

Two forecasting models, trained and compared on identical chronological splits of a building-energy CSV (a **dummy demo dataset is bundled**; use your real CSV for real results):

* **LSTM** - primary model (TensorFlow/Keras)
* **MLP** - comparison model using lagged target + calendar/weather/occupancy features
* **Ensemble** - links the two: `w x LSTM + (1 - w) x MLP`, with `w` fitted on the validation period, plus an
  80 % forecast range from validation errors (`src/ensemble.py`)

Scope: ML, plus an optional question-answering assistant over the results (`src/rag`, see
[Ask questions](#ask-questions-rag-assistant)). No frontend, API, database, dashboard or waste detection.
`data/dummy_building.csv` is a **synthetic demo dataset** (2 years, hourly, 17,520 rows) generated by
`tools/generate_dummy_dataset.py` so the whole pipeline can run end to end. The application code itself (`src/`) never
generates data. Nothing here has been trained on real data; **accuracy measured on the dummy data says nothing about real
buildings - train and evaluate on your own CSV for real numbers.**

## What it does

* Detects columns, validates the CSV (timestamps, duplicates, gaps, irregular intervals, missing/invalid
  readings, constant target, too little data) and explains which features are missing.
* Target = `demand_kw` (kW) when present, otherwise `energy_kwh` (kWh); output is labelled accordingly.
* Leakage control: chronological split (no shuffling across splits); scaler fitted on **train rows only**;
  gaps are only **forward-filled** (limited by `max_gap_hours`, no back-fill/interpolation); samples whose
  *target window* contains a missing/imputed reading are dropped, so metrics use real readings only;
  samples belong to a split only if their whole target window lies inside it.
* Both models use exactly the same samples (same origins, same train/validation/test periods).
* Features: lags 1, 2, 3, 24, 48, 168 h (lags the data cannot support are dropped and reported), hour/day-of-week/
  month as sin/cos, weekend flag, temperature, humidity, occupancy, equipment status (whatever exists).
* Metrics: MAE, RMSE, WAPE (reported as `null` when undefined), MAE by lead time, peak-demand error (kW only).
* The preferred model is chosen from **validation** performance (`selection_metric`, default RMSE), never from test.
  The ensemble is a candidate too. Its weight is fitted on validation, so its validation score is slightly
  optimistic; `selection.test_ranking_agrees` reports whether it also wins on the unseen test period.

## Run

Quick start with the bundled dummy data (`data\dummy_building.csv`), or put your own CSV in `data\`
(see `data\README.md`) and swap the path in the commands below:

```powershell
# 1. Validate the dataset (exit code 0 = passed, 1 = failed, 2 = could not read)
python -m src.data_validation --csv data\dummy_building.csv --report-json outputs\validation_report.json

# 2. Train the LSTM
python -m src.train --model lstm --csv data\dummy_building.csv

# 3. Train the MLP
python -m src.train --model mlp --csv data\dummy_building.csv
#    (or both: python -m src.train --model both --csv data\dummy_building.csv)

# 4. Evaluate + compare on the held-out test period (same CSV as training); also fits the ensemble
python -m src.evaluate --csv data\dummy_building.csv

# 5. Forecast the 24 h after the last timestamp of a CSV holding recent history (>= 7 days for the 168 h lag)
python -m src.predict --model best --csv data\dummy_building.csv          # preferred model (often the ensemble)
python -m src.predict --model ensemble --csv data\dummy_building.csv --format json   # report as JSON
python -m src.predict --model lstm --csv data\dummy_building.csv --origin "2024-11-15 00:00"   # backtest

# 6. Run the tests
python -m unittest discover -s tests -t . -v
```

Hyperparameters (all optional):

```powershell
python -m src.train --model lstm --csv data\dummy_building.csv --lstm-layers 2 --lstm-units 128 `
    --lstm-dropout 0.3 --learning-rate 0.0005 --input-hours 48 --horizon-hours 24 --epochs 150 --batch-size 64
python -m src.train --model mlp --csv data\dummy_building.csv --mlp-hidden 256,128,64
```
Defaults (`src/config.py`): 24 h input, 24 h horizon, 1 LSTM layer x 64 units, dropout 0.2, MLP 128-64 ReLU, Adam
(lr 1e-3), MSE, batch 32, max 100 epochs, early stopping on validation loss (patience 10, best weights restored),
seed 42. These are starting values, not tuned optima.

## Outputs

`artifacts\<lstm|mlp>\`: `model.keras`, `preprocessor.joblib`, `config.json`, `history.json`, `metadata.json`
(model version, split periods, features, CSV hash, measured validation metrics, library versions).

`artifacts\ensemble\ensemble.json` (written by `evaluate`): weights, component model versions, 80 % range
offsets per forecast step, validation/test metrics. If either model is retrained, rerun `evaluate` before
forecasting with the ensemble; `predict` refuses a stale ensemble.

`outputs\`: `evaluation_metrics.json`, `model_comparison.csv`, `test_predictions_<model>.csv` (lstm, mlp,
ensemble), `forecast_<model>_<origin>.csv/.json`, `forecast_report_<model>_<origin>.json/.md`, `plots\` (actual vs
predicted, error over time, MAE by lead time, peak-demand scatter for kW).

Forecast schema: `timestamp, actual_value, predicted_value, target_variable, unit, model_name, model_version,
forecast_generated_at`. Ensemble forecasts add `lower_value, upper_value` (80 % range) and `lstm_predicted_value,
mlp_predicted_value`. Evaluation files add `forecast_origin, horizon_step`. `actual_value` is empty for genuine
future timestamps.

Forecast report (`forecast_report_*.json`, same structure for every model; full schema in `src/report.py`):
`model` (name, version, components with weights), `forecast` (period, steps, future/backtest), `summary` (peak,
low, mean, kWh over the period), `prediction_interval`, `accuracy` (validation/test metrics of this exact model
version), `backtest`, `values` (per step: predicted, lower, upper, lstm, mlp, actual), `caveats`. The `.md` file
is the same report as readable tables; `predict` prints it (`--format report|table|json`).

## Ask questions (RAG assistant)

`src/rag` answers plain-language questions with Claude (`claude-opus-5-5`). It uses two kinds of context:

* **Forecast summary**, always sent in full: every model's validation/test errors (ensemble weights and range
  coverage included) and the latest `outputs\forecast_report_*.json` (falls back to the latest
  `forecast_*.csv`). It is built from the files in `outputs\`, so run `evaluate` and `predict` first.
* **Documents**, searched per question: `README.md`, `data\README.md` and every `.md`, `.txt` or `.pdf` file
  you put in `knowledge\` (manuals, tariffs, energy-saving guides). Documents are split into chunks of about
  200 words and searched with TF-IDF (scikit-learn, offline). The index is saved in `artifacts\rag\` and is
  rebuilt automatically when documents change.

```powershell
$env:ANTHROPIC_API_KEY = "sk-ant-..."         # or: ant auth login
python -m src.rag.ask "When is tomorrow's peak demand, and how reliable is that forecast?"
python -m src.rag.ask                          # interactive: one question per line, empty line quits
python -m src.rag.ask "When is the peak?" --json   # structured answer as JSON
python -m src.rag.ask "How do I train the LSTM?" --retrieve-only    # no API call: shows retrieved context
python -m src.rag.ingest                       # rebuild the index and list what was indexed
python -m src.rag.ingest --source knowledge --source D:\docs\hvac_manual.pdf    # index other files/folders
```

Options for `ask`: `--k` (chunks retrieved, default 5), `--effort low|medium|high|xhigh|max` (default
`medium`), `--model`, `--json`, `--show-context`, `--rebuild-index`. Claude replies in a fixed JSON structure
(structured outputs, `ANSWER_SCHEMA` in `src/rag/ask.py`): `answer`, `key_figures` (label + value with unit and
time), `confidence` (high/medium/low) with `confidence_reason`, `sources_used`, `caveats`. It is printed as
QUESTION / ANSWER / KEY FIGURES / CONFIDENCE / CAVEATS / SOURCES. Each question is answered on its own; there is
no conversation memory. Requests opt into Anthropic's
server-side refusal fallback (`fallbacks: "default"`), which re-runs a declined request on another model. Every
question is a paid API call.

Limitations: TF-IDF matches words, not meaning ("cooling" will not find "air conditioning"). Scanned PDFs
without a text layer yield no text. The assistant only knows what is in `outputs\` and the indexed documents.

## Web UI (Streamlit)

```powershell
streamlit run streamlit_app.py        # opens http://localhost:8501
```

| Tab | What it does |
|---|---|
| **Forecast** | Pick a model (best / ensemble / LSTM / MLP), a history CSV and an optional origin (for a backtest), then run. Shows peak, lowest, energy and typical error, a chart (forecast, 80 % range, LSTM and MLP lines, actuals), a table view, and downloads of the report (JSON, Markdown) and values (CSV). Opens on the latest saved report. |
| **Models** | Validation and test metrics for LSTM, MLP and the ensemble, the preferred model, ensemble weights and range coverage, error by lead time, the evaluation plots, and a Re-run evaluation button. |
| **Data & training** | Upload a CSV (saved to `outputs\uploads\`), validate it, and run the full pipeline: train both models, evaluate and fit the ensemble, then forecast. Training takes a few minutes on a CPU. |

The UI calls the same functions as the command-line tools and writes the same files. Charts (`src/ui/charts.py`)
keep one colour per model in every chart (Ensemble blue, LSTM orange, MLP aqua, actuals in text colour) and adapt to
Streamlit's light and dark themes. Hover a chart for all values at that time.

## Tests and their limits

Run `python -m unittest discover -s tests -t . -v`. Data validation/cleaning, chronological splitting, scaler
fitting, sequence/lag alignment, leakage checks, metrics and the train->evaluate->predict plumbing run without
TensorFlow (the plumbing tests use a persistence stub in place of Keras and verify nothing about model
accuracy). `tests/test_models.py` (real LSTM/MLP shapes and a tiny end-to-end run) executes only when TensorFlow
is installed and is skipped otherwise. Synthetic frames in `tests/helpers.py` are test fixtures only.

## Notes / limitations

* Forecasts are direct multi-step (one model call outputs all horizon steps); future weather/occupancy are not
  assumed known, so only values up to the forecast origin are used.
* Predictions are clipped at 0 by default (`clip_non_negative`).
* Evaluation requires the exact CSV used for training (checked by SHA-256) because the test period is defined by it.
* Small datasets give unreliable comparisons; the code refuses to train below the configured minimum samples.

## Dummy dataset

`data/dummy_building.csv` simulates a mid-size office: 2023-01-01 to 2024-12-30, hourly, columns
`timestamp, energy_kwh, demand_kw, temperature, humidity, occupancy, equipment_status`. It has daily/weekly/seasonal
patterns, holidays, HVAC load driven by temperature, short equipment outages and slow load growth. It passes
`src.data_validation` with no gaps or missing values. Regenerate or vary it with:

```powershell
python tools\generate_dummy_dataset.py --start 2023-01-01 --days 730 --seed 42 --out data\dummy_building.csv
```
